# ADR-1：多实例配置一致性采用「单控制面」

- **状态**：已接受（2026-11-11）
- **决策者**：架构 / 产品
- **影响范围**：v2.4 的配置版本号与乐观并发、v2.5 的多实例协作、部署文档

## 背景

网关可以多实例部署，但 2.4.0 之前每份配置都只存在于各自进程的内存里，落盘到本地的 SQLite / JSON。由此产生两个后果：

1. **配置漂移不可见。** 三个实例，运维在 A 上改了路由，B 和 C 不知道自己落后了。负载均衡把请求分到 B 时，返回 404 或 503，而 A 是正常的——现象是"时好时坏"，排查成本极高。
2. **并发写没有护栏。** 两个人同时编辑同一条路由，后保存的静默覆盖前一个，且没有任何日志说明发生过覆盖。

v2.4 补了版本号（`GET /api/config/state`）、`X-Config-Version` 请求头与 409、写前预检。这些解决的是**同一定义源内的冲突检测**，但"多个实例各有一份配置"这件事本身没变。

三条候选路线：

| 选项 | 做法 | 代价 |
|:--|:--|:--|
| **A 单控制面** | 只在**一个**实例上开 Dashboard，其余实例作为纯数据面；配置通过外部那套已有的通道（GitOps 下发、注册 API、共享配置文件）进入 | 需要部署纪律，不提供自动同步 |
| **B 外部存储** | 把 `IRouteRepository` / `IClusterRepository` 换成 Redis / PostgreSQL，多实例共享一份存储 | 引入新的故障域；配置读取进入每次请求的热路径或需要新的失效广播机制；要处理"存储不可用时网关是否降级" |
| **C CRD / 控制面进程** | 独立控制面 + watch 机制，实例订阅变更 | 等于重写为一个控制面产品，工作量在 3 人月以上，且把项目拖进 K8s 语义 |

## 决策

**选择 A：单控制面。**

- 文档与 README 明确写："Dashboard 是单实例配置入口，多实例部署时只在一个实例开启写权限。"
- 其余实例通过现有的注册 API（`/api/gateway/register-route`）或静态配置文件获得同一份配置。
- v2.4 的版本号与 409 是**同一实例内**的护栏，不承诺跨实例；`gateway_config_version` 指标暴露出来正是为了让运维能发现实例之间版本不一致。

## 后果

**正面**

- 零新增基础设施依赖。SQLite / 本地 JSON 继续可用，单机与多机部署是同一套代码。
- 不改请求热路径：配置读取仍在内存，`/metrics` 抓取不会打到外部存储。
- 保留所有退路：`IRouteRepository` 是接口，将来换 B 不需要改控制器层。

**负面**

- **不提供自动同步**。这是真实的运维负担：必须靠部署流程保证"只有一个写入口"。
- 版本号不能跨实例比较，`X-Config-Version` 在跨实例场景下没有意义。文档必须说清楚，否则会有人误以为它是分布式锁。
- 需要配套的告警建议：多个实例的 `gateway_config_version` 长期不一致 → 配置已漂移。

## 替代方案为何未采纳

- **B（外部存储）**：现在采纳，等于让"网关能不能路由"依赖 Redis 的可用性。为一个尚未被真实用户提出的需求，把故障面从 1 扩到 2，不划算。评估时间点：当出现"5 个以上实例且变更频率 > 10 次/天"的实际诉求时。
- **C（CRD）**：与 §7「不做 Kubernetes Ingress Controller」的边界直接冲突。

## 复审条件

出现下列任一情况时重新评估 B：

1. 有用户报告实例数 ≥ 5 且需要免人工同步；
2. 配置变更频率导致"部署纪律"实际不可执行；
3. 需要灰度发布（v2.5 的权重灰度）在**跨实例**维度生效。
