# ADR-3：分布式限流只保留扩展位，不做实现

- **状态**：已接受（2026-11-11）
- **决策者**：架构 / 产品
- **影响范围**：`rate-limit` 插件、`gw-rl-*` 内置策略、README 的不做清单

## 背景

多实例部署时，现有的限流是**每实例一份计数器**。三个实例、每实例 100 QPM，实际放行上限是 300 QPM。运维在 Dashboard 上填 100，看到的是 100，真实行为却是 300——又是一个"填了不报错但不生效"。

要做到真正 100 QPM，必须有一个跨实例共享的计数器，常见做法是 Redis + Lua 脚本（或 token bucket in Redis）。

问题是：这个方案会把 Redis 放进请求热路径。

| 方案 | 一致性 | 可用性影响 |
|:--|:--|:--|
| 本地计数器（现状） | 每实例精确，全局放大约 N 倍 | 无外部依赖 |
| Redis 集中计数 | 全局精确 | **Redis 抖动 = 全站 5xx 或全放行**，取决于降级策略 |
| 本地 + 周期同步配额 | 近似（允许 N× 误差窗口内） | 弱依赖，可降级为本地限流 |

第三种其实是最务实的工程解，但它需要额外的配额分配协议（谁分多少、实例扩缩容怎么重新分配），复杂度不在限流本身，而在**协调**。

## 决策

**保留扩展位，不做实现。**

1. `rate-limit` 插件的策略接口按"可替换计数器后端"设计，本地计数器只是默认实现；不做分布式实现。
2. 文档明确写：**限流是每实例配额**，多实例部署时全局上限 = 单实例上限 × 实例数。这句话进 README 的不做清单，避免有人按 100 QPM 的预期上线。
3. `gw-rl-100pm` 等内置策略保持单机语义，不暗示分布式能力。

## 后果

**正面**

- 网关的可用性不依赖任何外部存储。这条底线比"限流数值精确"重要——限流失效最多被打穿，Redis 挂了是整站不可用。
- 调用方接口不变：将来接分布式后端时，插件配置与路由字段（`RateLimiterPolicy`）都不需要改，只是后端换成远程计数器。这正是"保留扩展位"的意义。
- 与 ADR-1（单控制面）一致：既然承认是单写入口，就不必为多实例的一致性付出热路径代价。

**负面**

- **限额不精确这件事必须靠文档传达**，无法靠代码保证。写成指标也许会更好：暴露 `gateway_rate_limit_quota_scope{scope="instance"}`，让看板一眼看出这是单机配额。
- 若用户确实需要全局精确限流，我们只能给"在前面挂一个 Redis 限流中间件"的建议——这属于把问题推给用户，需要在文档里给足迁移示例，否则会被认为是推诿。

## 替代方案为何未采纳

- **直接做 Redis 实现**：引入硬依赖，且要回答"Redis 不可用时放行还是拒绝"这个没有正确答案的问题。默认放行 → 限流形同虚设；默认拒绝 → 网关变成 Redis 的附属品。
- **本地 + 周期配额同步**：技术上可行且更稳，但需要先有实例发现机制（谁是实例、有几个），而 ADR-1 已经把多实例协作推迟到 v3。现在做等于跳步。

## 复审条件

出现下列任一情况时启动实现评估：

1. 用户明确要求全局精确限流，且能接受外部依赖；
2. v3 的实例发现机制落地，使"本地 + 配额同步"成为低成本选项；
3. 出现因每实例配额导致的上游过载事故（有实际案例，而非理论担忧）。
