# ADR-4：RBAC 按「爆炸半径」切三档，且默认隐式管理员

- **状态**：已接受（2026-11-11）
- **决策者**：架构 / 产品
- **影响范围**：`Aneiang.Yarp.Dashboard.Infrastructure.Auth/*`、`Gateway:Dashboard:Auth` 配置、面板所有写操作

## 背景

Dashboard 到 v2.5 为止只有"能进/不能进"这一个维度：认证通过就是全能管理员。这在实际部署里很快不够用——

- 值班的同学需要看板确认"服务还在不在"，不应该顺手能把生产路由删掉；
- 日常改路由、绑插件的人（运维）需要一个能干活、不用每次找人授权的账号；
- 但**装插件**和**改通知地址**这两类操作不该和"改路由"同级：能改通知地址的人可以把告警静默掉，能装插件的人可以引入任意代码。

同时有一条不可退让的约束：**升级不能锁死存量部署**。现在只有一个 `JwtUsername`/`JwtPassword`、或者干脆没开认证的部署，升级完之后必须还能进、还能改。

## 决策

### 1. 三档角色，切分依据是"能造成多大破坏"，不是"资历"

| 角色 | 能做什么 | 拒绝方式 |
|:--|:--|:--|
| `viewer` | 看所有页面 | **按方法拒绝**：任何非 GET/HEAD/OPTIONS 一律 403 |
| `operator` | 改网关：路由、集群、插件绑定、环境切换、提升 | **按路径拒绝**：仅"决定谁能改网关"的那几个端点 |
| `admin` | 上述之外，还能装/卸插件、改通知目标 | — |

viewer 用**方法**而不是路径列表拒绝，是因为路径列表会随页面增加而失效：新加一个页面就出现一个新的写入口，而没人会记得回去更新那张表。方法白名单不会漏。

operator 用**路径**拒绝，且列表是"默认允许"的：新增的运维端点自动可用。代价是必须记得给真正的控制面端点加标记——这个代价被显式接受，理由是"运维改不了路由"比"运维能碰一个新端点"更常见地打断正常工作。

### 2. 角色放在 token 的 `role` claim 里

不在每个请求里查账号表。副作用是**降权需要重新登录**（token 8 小时有效）——对降权来说这恰恰是想要的语义：不能靠"改完配置等他下次刷新"来撤销权限。

### 3. 无法归属的身份一律隐式管理员

以下三种情况解不出角色，全部按 `admin` 且标记 `Implicit: true`：

- `AuthMode = None`（根本没开认证）；
- `AuthMode = ApiKey`（机器凭证，背后没有账号）；
- 自定义 `AuthorizeRequest` 委托（宿主自己决定，我们无法反推）。

理由是**没有账号可以归属时，假装有角色只会锁死存量部署**。`Implicit` 标记传给前端，用来避免显示一个"只读"横幅——那会是一句谎话。

### 4. 认证关闭时不做任何限制

`AuthMode = None` 意味着这台机器的网络边界就是安全边界。此时再叠一层角色检查，等于"开了认证才能用"，是把安全责任推给一个并不存在的账号体系。

## 配置形态

```jsonc
{
  "Gateway": {
    "Dashboard": {
      "Auth": {
        "AuthMode": "CustomJwt",
        "JwtSecret": "至少 32 字节的随机串",
        "JwtPassword": "admin-fallback-password",   // 仅当 Users 为空时使用
        "Users": [
          { "Username": "alice", "Password": "…", "Role": "admin"    },
          { "Username": "bob",   "Password": "…", "Role": "operator" },
          { "Username": "carol", "Password": "…", "Role": "viewer",
            "TwoFactorSecret": "BASE32SECRET" }
        ]
      }
    }
  }
}
```

- `Users` 为空 → 退回 `JwtUsername`/`JwtPassword`，按 `admin` 处理。**这就是升级前的行为**，一个字段都不用改。
- `Role` 缺省或无法识别 → 按 `admin` 处理并在日志里报错。角色名打错不该让面板起不来，但也不能静默降权。
- `TwoFactorSecret` 逐账号配置，缺省继承面板级 `TwoFactorSecret`。

## 后果

**正面**

- 值班账号可以只读，误删生产路由这一类事故从"靠人靠谱"变成"结构上做不到"。
- 拒绝理由带 `reason` 码（`read-only` / `admin-required`），前端翻成本地语言。看到的是"当前账号为只读，不能修改任何配置"，而不是一个 403 和一句英文。

**负面**

- **operator 的路径黑名单会漏**。新增一个控制面端点而忘了加进去，运维就能碰。接受这个风险，因为反方向（运维被自己的面板挡住）每天都在发生。
- **前端隐藏按钮不是安全边界**。它只避免"点了一个注定失败的按钮"。真正的保证在过滤器里，因为页面在加载和点击之间可以被替换成一个权限更高的 token。
- **`data-requires-write` 是逐处标记的，会有遗漏**。遗漏的后果是"按钮还在，点了报只读"——可接受但不理想。判断依据是：宁可漏标记，也不要因为一个粗暴的全局限定把"退出登录"也一起藏了。

## 什么条件下应该重新评估

- 需要按**环境**分权（"只能改 staging"）——现在的角色是全局的，而多环境已经存在于同一个面板里；
- 需要审计到"谁在什么时候改了什么"的强合规要求——现在有 `ConfigChangeAuditLog`，但没有把 principal 串进去；
- 接入了真正的 IdP（此时 ADR-1 的单控制面与"自带 IdP 不做"的边界都要重新看）。
