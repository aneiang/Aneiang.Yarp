# Aneiang.Yarp 产品规划（2026 Q4 – 2027 H1）

> 角色：产品负责人视角。所有判断均以当前仓库代码事实为基线（初版基于 `v2.3.0.30`，本文档已按 `2.3.0.40` 更新交付状态）。
> **版本口径**：文中的 v2.4 / v2.5 / v2.6 是开发批次代号，不是发布版本。`2.3.0.30` 之后的全部改动统一以 `2.3.0.40` 对外发布（`2.3.0` = YARP 版本，`40` = Aneiang.Yarp 版本）。  
> 目的：不是列功能，而是回答三个问题——**我们现在是什么、卡在哪、接下来该做什么、以及明确不做什么**。

## 0. 一页结论

1. **产品定位已经成立，但只覆盖了「装得上」这一段，没覆盖「敢上线」这一段。** 面板、插件、AI 助手这些"看得见"的部分完成度很高；配置变更的安全网、生产可观测出口、多实例一致性这三块几乎是空的。这是本产品从"好用的开源项目"跨到"生产级网关"的唯一门槛。  
   → **2.3.0.40 后：变更安全网与可观测出口已补齐，多实例按 ADR-1 明确锁定「单控制面」。**
2. **最危险的不是缺功能，而是"填了不报错、也不生效"的字段。** 路由表单里的 `AuthorizationPolicy` / `CorsPolicy` / `RateLimiterPolicy` / `OutputCachePolicy` 引用的都是"代码里注册过的策略名"，而网关侧根本没有 `AddAuthorization` / `AddCors` / `AddRateLimiter` 注册。用户填任何值，要么静默失效、要么整条路由在端点构建时炸掉。这跟我们刚修的「开关≠生效」「Destinations 被清空」是同一个病根：**配置写入路径缺乏校验与语义约束**。  
   → **已解决**：四个字段改为下拉 + 9 个内置 `gw-*` 策略 + 保存时拒绝未注册名；并且补了那条最容易漏的 `app.UseRateLimiter()`。  
   |  |  |  |  |  
   | --- | --- | --- | --- |
3. **插件模型只覆盖了"中间件"一种形态。** `PluginCapability` 只有 `RequestMiddleware | ProxyPipeline | Dashboard | BackgroundService`，没有 YARP 最常用的两个扩展点——自定义 `LoadBalancingPolicy` 和 `Transform`。这意味着"权重灰度""流量镜像"这类流量治理需求，**写插件是做不到的，必须先动框架**。这是路线图排序的硬约束。
4. **建议把主线从"加功能"切换到"加保障"。** 未来三个版本的主题依次是：**能上生产（变更安全）→ 敢做灰度（流量治理）→ 平台化（多环境/多租户/生态）**。
5. **明确守住边界。** 不做 API 门户、不做 IdP、不做日志分析引擎、不做 mesh sidecar。我们的护城河是"YARP 原生语义 + 一个能看懂的控制面"，不是把自己做成 Kong。

## 1. 我们到底在做什么（定位与边界）

### 1.1 一句话定位

> **YARP 的「生产化外壳」**：把微软那个"只负责转发、刻意不做控制面"的库，补齐成一套能配置、能观测、能审计、能交付的网关。

微软对 YARP 的定位非常克制：它给你 `IHttpForwarder`、给你配置模型、给你扩展点，然后明确说"配置怎么来、谁来管、出问题怎么看，你自己解决"。**这句"你自己解决"，就是我们整个产品的市场。**

### 1.2 用户分层（三类人，诉求互相冲突）

| 人群                        | 占比估算 | 真实诉求                                    | 现状满足度                          |
| :------------------------ | :--- | :-------------------------------------- | :----------------------------- |
| A. 单体/小团队后端               | ~70% | 三行代码接进来，打开面板能看懂，别让我读文档                  | **高**（这是当前优化得最好的部分）            |
| B. 平台/基础设施团队              | ~25% | 多环境、多实例、变更管控、能不能接我们的 Prometheus/Grafana | **低**（几乎没覆盖，也是付费/长期使用意愿最强的一层）  |
| C. 从 Kong/APISIX/Nginx 迁移 | ~5%  | 能力对齐表、迁移路径、性能对比数据                       | **中**（文档有对比表，但缺可验证的 benchmark） |

**战略判断：当前产品把 90% 的精力花在 A，而 B 才是决定项目能否被长期采用的那一层。** 下一阶段的重心必须向 B 偏移，但不是抛弃 A——A 的体验是我们的获客入口。

### 1.3 做什么 / 不做什么

**做（控制面 + 策略面 + 观测面）**

- 配置生命周期：编辑 → 校验 → 应用 → 审计 → 回滚
- 网关策略：安全（WAF/限流/IP）、稳定性（重试/熔断/超时）、流量（压缩/缓存/灰度）
- 观测：面板 + 指标出口 + 告警
- 开发者体验：一行接入、Docker/Helm/模板

**不做（并且要在文档里明确写出来，降低预期）**

- ❌ API 设计与文档门户（交给 Swagger/Scalar）
- ❌ 身份提供商 / SSO 服务端（对接 OIDC 即可）
- ❌ 日志存储与分析引擎（SQLite 做热数据 + 推给 Loki/ES）
- ❌ Service Mesh 数据面 / sidecar
- ❌ 完整 K8s Ingress Controller（可做 CRD 桥接，不做全量对齐）

> **状态：✅ 已于 2.3.0.40 写进中英 README**（「我们明确不做的事」/「What We Deliberately Do Not Build」），六条都带理由与替代方案，另补了「分布式限流」一条。

### 2.2 配置表达力（关键发现）

`ConfigurationSchema.json` 是从 YARP 配置模型完整生成的——**路由/集群的所有字段在 JSON 模式里都能填**：

- 路由：`Match`（Path/Hosts/Methods/Headers/QueryParameters）、`Transforms`（26 种内置）、`Order`、`MaxRequestBodySize`、`Timeout`、四类策略引用
- 集群：`Destinations`、5 种 `LoadBalancingPolicy`、`SessionAffinity`（4 策略 + Cookie 细节）、`HealthCheck`（Active/Passive/AvailableDestinationsPolicy）、`HttpClient`、`HttpRequest`、`Metadata`

**结论：YARP 的配置面，我们没有缺口。缺的是"这些字段能不能被安全地填"。**

## 4. 五个真实痛点（带证据）

### 4.1 【P0】引用型策略名是"静默炸弹"

**现象**：路由表单能填 `AuthorizationPolicy: "Default"`，但网关侧从未 `AddAuthorization` / `AddCors` / `AddRateLimiter` / `AddOutputCache`。填了之后 YARP 在构建路由端点时找不到策略名——轻则该路由 500，重则代理初始化失败。

|                                                                                 |         |                                                                   |
| ------------------------------------------------------------------------------- | ------- | ----------------------------------------------------------------- |
| **证据**：`ConfigurationSchema.json` 暴露了四个 `*Policy` 字符串字段；\`grep AddAuthorization | AddCors | AddRateLimiter`在`src/\` 下**只有 Dashboard 自己的 OutputCache**，网关侧零注册。 |

**影响**：这是最坏的一类 bug——**用户按 UI 提示填了值，系统不报错，线上偶发失败**。和「启用≠生效」属于同一族，但更隐蔽，因为它发生在前端完全看不出异常的地方。

**判断**：不是文档能解决的，必须改产品交互。

1. 后端提供 `GET /api/policies/available`，反射出已注册的策略名；
2. 表单把四个字段从"自由文本"改为"下拉 + 空选项"，空 = 不启用；
3. 保存时校验策略存在性，不存在直接 400 并说明"该策略需在你的 `Program.cs` 中注册"；
4. Dashboard 顺带内置一组标准策略（`gw-anonymous` / `gw-cors-public` / `gw-cache-60s`），让开箱就有东西可选。

**代价**：约 2 人日。**收益：消除一整类线上事故。**

> **状态：✅ 已交付（2.3.0.40）。** 四点判断全部落地。实现时多发现一件事：策略注册了但 `app.UseRateLimiter()` 没进管道，等于换个地方继续静默 —— 已一并补上。这个坑没写在原判断里，是"以为修好了"的典型。

---

### 4.2 【P0】变更没有"预检 / 差异 / 灰度"

**现状**：点保存 → 立即写入 → 立即对全部流量生效。唯一的保护是"回滚"（事后）。

**为什么会出事**：集群/路由是**互相引用**的图。改集群名、删 destination、改 Match Path，影响面远大于表单上那一行字。用户没有机会在应用前看到"我这一改，会让 3 条路由失去目标"。上次 Destinations 被清空的事故，本质就是"一次写回没人拦"。


**判断**：这是"敢不敢上生产"的核心开关，优先级高于任何新插件。

- 预检：`POST /api/clusters/validate`（不落库，跑一遍 YARP 的 `ConfigValidator` + 引用完整性 + 连通性探测）
- 差异：保存前弹"变更摘要"，人话描述（`删除 2 个目标节点：10.0.0.5:8080、10.0.0.6:8080`），而不是 JSON diff
- 灰度：支持"仅对 1 个 destination / 1 个副本应用，观察 N 秒，失败自动回滚"
- 版本号：每次写入递增 `config_version`，提交时带 `If-Match`，冲突返回 409

**代价**：约 17 人日（预检 5 + diff 4 + 灰度 8，版本号 5 可并行）。

> **状态：🟡 四项里交付三项（2.3.0.40），灰度留给 v2.5。**

|   |   |   |   |
| - | - | - | - |

> | 判断项     |  状态 | 说明                                                         |
> | :------ | :-: | :--------------------------------------------------------- |
> | 预检      |  ✅  | `POST /api/config/validate`，字段精到 `Destinations.d1.Address` |
> | 差异      |  ✅  | 人话摘要（"删除目标节点 d1：http://…"），删除项二次确认                         |
> | 版本号 409 |  ✅  | `X-Config-Version`，采样式而非线性化 CAS                            |
> | 灰度      |  ⬜  | 依赖 ADR-2 的 LB 扩展点，v2.5                                     |
>
> **2.3.0.40 交付时漏掉的一段**：预检与版本号只注入在 Dashboard 的两个控制器上，而自注册、批量导入、历史回滚、AI 助手这四条写路径完全绕过。**"预检可以被绕过"等于没有预检**，而且被绕过的恰恰是机器写入——比人手点表单更危险。2.3.0.40 用核心库 `IConfigurationGuard` + 批量校验把四条约全部收口。

### 4.3 【P0-架构】多实例配置一致性没有方案

**现状**：配置存本地 SQLite，每个网关副本各存一份；变更通过本地 API 写入。**两个副本 = 两份真相。**

**这不是"功能缺失"，是定位问题**。三条路：

- **A. 锁定"单控制面"**：明确文档写"一个网关集群只跑一个控制面实例，数据面可多副本共享同一份 SQLite（网络挂载）或不共享"。—— 最省力，但限制了横向扩展。
- **B. 引入外部存储**（Postgres/Redis）：配置集中，副本只读。—— 复杂度陡增，且我们刚刚移除了 Redis 依赖。
- **C. K8s CRD**：配置即资源，交给 etcd 保证一致性。—— 只服务 K8s 用户。

**产品建议：v2.x 明确选 A，把 B 留给 v3。** 理由：过早引入分布式协调会把这个项目的复杂度拉爆，而 A 已经能覆盖 80% 的真实部署（多数团队网关是 2-3 副本 + 一个管理入口）。关键动作不是写代码，是**把定位写进文档，并在面板上显示"当前配置版本 + 各副本版本一致性"**（如果检测得到）。

> **状态：🔵 已按 A 决策并落成 ADR（2.3.0.40）**：`docs/adr/ADR-001-single-control-plane.md`。  
> 代码侧兑现的是"让漂移可见"这一半：`gateway_config_version` 指标 + `GET /api/config/state`。多个实例版本长期不一致即可告警。  
> 明确不做的：跨实例自动同步、分布式锁。复审条件是"实例数 ≥ 5 且需免人工同步"或"灰度必须在跨实例维度生效"。

### 4.4 【P1】观测数据出不去

**现状**：面板做得很好（本轮刚把三页插件流程打通），但数据**只在这个面板里活着**。没有 `/metrics`，没有 OTel。

**为什么这是问题**：B 类用户（平台团队）的第一句永远是"能不能接我们的 Prometheus"。接不上，他们的评价就是"玩具"。而我们有 `LockFreeStatistics` 这种现成的高性能计数器，做一个文本 exporter 的成本极低。

**判断**：**投入产出比最高的一项**。

- `GET /metrics`（Prometheus 文本格式，零依赖手写即可）：3 人日
- YARP 埋点 Activity（`IForwarderErrorFeature` + 自定义 `ActivitySource`）：5 人日
- 面板新增"容量视图"：连接池使用率、上游耗时分解、QPS 水位：4 人日

> **状态：✅ 2.3.0.40 三项全部交付。**
>
> - ✅ `/metrics` 出口（2.3.0.40），11 个 Grafana 面板随包提供
> - ✅ 容量视图里的**连接池**（2.3.0.40）：YARP 不暴露池状态，但 .NET 8+ 的 `System.Net.Http` 内置 Meter 有 `http.client.open_connections`，挂 `MeterListener` 即可拿到真实连接数 —— 2.3.0.40 时我判断"做不到"，这个判断是错的
> - ✅ 上游耗时分解与 OTel Activity（2.3.0.40）：埋点在核心库（只 `new ActivitySource`，零新依赖），导出与 SDK 全部落在 Dashboard；`/tracing` 页不开 exporter 也能看瀑布图
>
> **原来估的和实际做的差在哪**：估的是"Activity 埋点"，实际做出来的是"能定位到哪一跳"——`gateway.forward` 记下 route / cluster / destination，`gateway.plugin <id>` 让每个插件的耗时单独成段，`gateway.short_circuited` 把"插件拦掉了"和"上游挂了"分开。埋点本身两天就够，剩下的时间全花在"让别人不用装 Jaeger 也能看"这件事上，而那才是这项真正减少排查时间的部分。

### 4.5 【P1】插件模型只覆盖"中间件"，流量治理做不了

**证据**：`PluginCapability { RequestMiddleware, ProxyPipeline, Dashboard, BackgroundService }`。没有 LB、没有 Transform、没有 `IProxyConfigFilter`。

**后果**：YARP 生态里最常用的两个扩展点（自定义负载均衡策略、自定义请求变换）**无法以插件形式交付**。于是"按 header 灰度""按权重分流""A/B 测试""流量镜像"这些需求，全都卡在框架层，写多少个插件都没用。

**判断**：如果流量治理是产品主线之一（我认为是），**必须先做框架扩展**：

1. 插件 DI 期允许注册 `ILoadBalancingPolicy` 与 `ITransformProvider`（YARP 本身支持 DI 注入）
2. 用 `Metadata` 承载插件配置（如 `Metadata["weighted:weights"] = "a=90,b=10"`），保持配置模型零侵入
3. 先交付一个"权重路由"作为样板插件，验证扩展点是否够用

这是唯一一项"必须动内核"的改动，也是 v2.5 的前置依赖。

> **状态：✅ 2.3.0.40 已交付。**
>
> **一处需要修正的原判断**：上面写的"必须先动内核"过头了。核实代码后发现框架自己已经在 DI 里注册了这两个扩展点 —— `AneiangYarpServiceCollectionExtensions` 注册了 `IpBasedLoadBalancingPolicy`，`DashboardServiceCollectionExtensions` 注册了 `DownstreamCaptureTransformProvider`。所以 YARP 侧一行都不用改，缺的只是两件小事：
>
> 1. `PluginCapability` 加 `LoadBalancingPolicy` / `Transform` 两个枚举值；
> 2. 给插件一个**容器构建期**的 `ConfigureServices(IServiceCollection)` 入口。
>
> 工作量因此从 5d 压到约 2d。结论不变，但风险等级从"动内核"降为"加钩子"。
>
> **实施时的第二个发现（比上面更关键）**：`IGatewayPlugin.ConfigureServices` **不是**容器构建期入口 —— 它在 `PluginRuntimeDomain.PrepareAsync` 里对一个**新建的** `ServiceCollection` 调用，宿主容器当时已经冻结。在那里注册 `ILoadBalancingPolicy` 会被无声丢弃，等于把"填了不生效"这个老毛病复制到插件层。所以钩子是独立接口 `IGatewayPluginHostServices`：DI 期实例化插件（要求无参构造）、注入宿主的 `IServiceCollection`、由 `Aneiang.Yarp.Plugin.Abstractions` 里的 `AddPluginHostServices` 统一扫描执行。

> **v2.5 可以复用的 v2.4 成果**：#3 的"错误率超阈值"直接读本轮的 `/metrics` 计数器；#2 的策略名走本轮的策略目录，不再需要单独的校验逻辑；灰度前后的对比可以直接用 `gateway_requests_total{route,cluster}` 的分组能力。

> **2.3.0.40 复盘（#1/#2）**
>
> - **扩展点的真实约束被找到了**：`IGatewayPlugin.ConfigureServices` 跑在**插件运行时域**（`PluginRuntimeDomain.PrepareAsync` 里新建的 `ServiceCollection`），宿主容器此时已经冻结，所以在那里注册 `ILoadBalancingPolicy` 永远不会被 YARP 看见。ADR-2 原来写的"开放扩展点"如果不解决这一层，就只是换了个地方继续静默。解法是新增 `IGatewayPluginHostServices`，在 DI 期实例化插件并注入宿主集合。
> - **没有选 PowerOfTwoChoices 凑合**：它读 `Weight`，但只在两个随机节点之间用它做平局裁决，实际比例会漂移。灰度要的是"说是 10% 就是 10%"，所以实现了平滑加权轮询，并用 100 次/1000 次断言把精确性钉住。
> - **顺手修掉一个会直接毁掉灰度的隐患**：集群没有显式策略时接口返回 `"Default"`，而这个值会被 JSON 编辑器原样写回，YARP 没有叫 `Default` 的策略 —— 任何一次"只改权重"的保存都会把集群改坏。

> **2.3.0.40 复盘（#5 追踪）**
>
> - **埋点和导出的依赖必须分处两地**：核心库只 `new ActivitySource("Aneiang.Yarp")`，用的是框架自带的 `System.Diagnostics.DiagnosticSource`；OTel SDK、instrumentation、OTLP exporter 全在 Dashboard。否则一个"没打算接 Jaeger"的用户也会被动背上 exporter 的依赖和它连不上 collector 时的日志噪音。
> - **瀑布图的第一版是错的，错在假设了 API 的语义**。按 `ParentSpanId is null` 找根，结果根从来不在缓冲区里（ASP.NET Core 的请求 span 由 `Microsoft.AspNetCore.Hosting.HttpRequestIn` 直接 `new Activity(...)` 创建，**不经 ActivitySource**，`Source.Name` 是 `Microsoft.AspNetCore` 而不是我以为的 `Microsoft.AspNetCore.Hosting`），于是"根"退化成 `proxy.forwarder`，整条链路挂错了位置。现在改成按 `StartedAt` + 父链深度定层，并优先认 `gateway.forward` 作根。
> - **计数器一开始在说谎**：`sampledTraces` 数的是**采样判定次数**，而 `AddAspNetCoreInstrumentation` 的 `Filter` 跑在采样**之后** —— 控制面请求已经被问了"要不要采样"，回答完了才被丢掉。于是页面上"采样 12"对着"缓冲 1 条"，像坏了。两处修：字段与页签文案改成"判定次数"并给出原因；`clear` 连计数器一起归零。
> - **丢弃的 trace 仍然会创建 activity**（标记为仅传播上下文）。如果不过滤 `!data.Recorded`，缓冲区会被未采样的 span 灌满，而页面写的是"显示的就是被采样到的"，两边就矛盾了。

> **2.3.0.40 复盘（#6 故障注入）**
>
> - **插件在管线里的位置不是风格问题，是这件事有没有意义的问题**。故障注入必须排在 `ProxyPluginOrder` 的最后一位（紧挨 forwarder）：只有在这个位置，注入的 5xx 对重试、熔断、指标、告警、灰度来说才**与上游真的坏了无法区分**。放到最外层，那些被演练的组件根本看不见故障，演练会"全部通过"，而这比不做演练更危险 —— 它给出了一份假的信心。
> - **"一键关闭"的真实开关只能是绑定的 `enabled`，不是插件开关**。插件管理器会拒绝禁用"仍有绑定的插件"（409 `Remove plugin bindings first`）—— 这是防止误点把演练配置一起弄丢的护栏，也意味着文档里写"去插件列表关掉它"是错的。第一版日志与帮助文案都这么写，端到端跑一遍就被推翻了。现在统一为"关掉这条绑定"：下一个请求立刻不再注入，配置保留，随时可以重开同一场演练。
> - **演练最先撞出来的往往不是被测组件的问题**。注入 503 → 重试耗尽 → 日志里冒出 `Headers are read-only` 未处理异常，追下去发现 `RequestRetryMiddleware` 在 `CopyToAsync` 之后写 `X-Retry-Count`，把上游真实的 5xx 变成了一个 500。这个 bug 一直都在，但要"路由配了重试"且"连续失败到用尽重试"才会显形，正常流量几乎撞不到。修好后补了 `RequestRetryResponseTests`，断言的是"头写在响应启动之前"而不是"最终有头"。
> - **概率不能靠统计来测**。`FaultInjectionPlanner.Plan(config, headerReader, sample)` 把随机数挪到调用方，概率边界就能精确断言（0.5 时 `0.49` 命中、`0.5` 不命中），不用发一千个请求去看比例像不像 —— 那种测试又慢又会偶发变红。

> **2.3.0.40 复盘（#1a 环境隔离）**
>
> - **多环境的实现方式决定了它有没有用**。行级隔离（每表加 `EnvironmentId`）看起来"更正统"，但它把三个环境塞进同一个文件、同一个连接、同一套 SQL：dev 的一次误删和 prod 只隔了一个 `WHERE`。改成每环境一个 SQLite 文件之后，隔离是文件系统级的，dev 库怎么坏都碰不到 prod；而且**不需要动任何表结构、任何 SQL、任何仓储**，358 个既有测试一个都没改。
> - **`prod` 复用原连接串是这次交付里最重要的一行代码**。如果按"环境名"机械地给所有环境加后缀，存量部署升级后会发现配置全没了 —— 而这正是最不该发生的升级事故。现在的规则是：运行环境拿到的连接串与升级前**逐字节相同**，其余环境才派生。
> - **必须显式拆开"正在转发"和"正在编辑"**。两者合成一个状态是省事的写法，但那样一来"打开 staging 看一眼"就等于把生产流量切到 staging。现在的做法是：切环境只改面板的读写目标，发布快照前判断目标是不是运行环境，不是就拒绝。**这个判断放在发布器的唯一入口，而不是每个调用点** —— 写入路径有五条（单条 / 批量 / 导入 / 回滚 / 自注册），漏一条就是一次生产事故。
> - **切环境要重载工作集，不能只换连接**。工作集是后续每次保存的数据源，留着旧环境的内容就会把旧环境的全量配置写进新环境 —— 与"没生效"相反方向的泄漏，而且更难发现。读库失败时把视图回滚回去，不留下一个半开的环境。
> - **缓存键不带环境名，等于切换没生效 5 秒**。端到端第一次跑就撞上了：切到 dev 之后路由列表还是 prod 的，因为两个查询服务把键硬编码成 `dashboard:routes:query`。现在键里带环境名，`InvalidateQueryCaches()` 也改成向服务要失效而不是按硬编码键名删 —— 后者在键名变化后是**静默失效**的，这种"改了但没报错"的坑不该再挖一次。
> - **环境名要进文件名，就必须在配置期拦住路径穿越**。`../prod` 这种名字如果放过去，`Path.Combine` 会把库指到别处。白名单校验只在 registry 一处做，因为那是唯一接受名字的地方。

## 10. 需要你确认的四个问题

> **状态：🔵 四个问题你已在开工时按建议放行**（原话"就按你的计划全都实现"），执行时按此前提推进。下面补记实际执行结果，便于日后回看当时的取舍。

1. **你更想解决"更多人用"还是"更敢用"？** 前者做 DX（镜像/模板/文档），后者做变更安全。我的排序是"更敢用"，因为 B 类用户的留存和口碑更强。<br>→ **按"更敢用"执行**：v2.4 六项全是保障类，零新插件；DX（镜像/Helm/模板）推到 v2.6。
2. **是否接受 v2.4 一个插件都不加？** 那一版全是"保障类"工作，没有可炫耀的新功能，但对项目长期价值最大。<br>→ **已接受**：v2.4 未新增任何插件，新增的是校验/指标/并发三块基础设施。
3. **多实例走 A 方案（单控制面）你能接受吗？** 如果不能，v2.4 就要塞进外部存储，工期翻倍。<br>→ **已接受**，落成 ADR-1。代价是"不自动同步"，用 `gateway_config_version` 指标让漂移可见。
